# MediFlow 피부·두피 AI 프로젝트 최종 상세 보고서

기준일: 2026-09-28  
범위: 피부·두피 이미지 분류 연구의 시작부터 현재 저장된 결과와 다음 연구 계획까지  
상태: **공개 데이터 기반 후보 선정·패키징과 Colab 실행 비용 비교 완료. 실제 장비·현장 데이터 검증과 시스템 통합은 미완료.**

이 보고서는 발표 자료의 1~4차 상세 설명을 한 파일로 묶고, 팀원 저장소와의 연결 범위, 현재 모델 선정, 향후 계획을 덧붙인 읽기용 본문이다. 수치의 원본은 `results/`의 JSON·CSV·후보 패키지이며, 본문에 링크한 도메인별 연구 문서는 더 세밀한 실행 근거다. **계획, 실행, 관찰 결과를 구분한다.** 실제 환자·현장 촬영 성능이나 의료적 효용을 공개 데이터 점수로 대신 주장하지 않는다.

## 이 문서를 읽을 때의 세 가지 기준

1. `skin`은 **USB 현미경 피부 병변 10클래스**, `web_skin`은 **웹캠 정면 얼굴 5클래스**, `hair`는 **USB 현미경 두피**다. Hair에는 기존 5클래스와 새 `양호`를 포함한 별도 6클래스 과제가 있다. 네 과제의 전체 정확도를 한 순위로 비교하지 않는다.
2. **Validation은 실험·후보 선정**, **Test는 선정 후 평가**에 사용한 기록을 우선한다. 초기 실험의 평가 절차와 데이터 버전은 뒤의 Clean 결과와 다를 수 있다.
3. 이 문서의 `완료`는 저장된 코드·보고서·패키지에서 확인한 범위다. 식별 정보가 없어 검증하지 못한 사람·병변·촬영 세션 수준의 누수, 실제 기기의 지연·전력, 임상적 타당성은 완료로 간주하지 않는다.

## 1. GitHub 연결 전: 데이터 수집부터 첫 분류 모델까지

> 이 문서는 **첫 데이터 수집·전처리·학습 당시**를 설명한다. 뒤에 발견한 데이터 중복이나 2단계 미세조정 결과를 이 시점의 성과로 소급하지 않는다. 수치는 초기 `results/*/1_training/`의 저장 JSON과 당시 연구 문서에 근거한다. 원천 데이터 사이트의 규모는 당시 문서에 기록된 규모이며, 원천 전체 ZIP은 현재 로컬에 없어 새로 계수한 값이 아니다.

### 발표 흐름

1. Kaggle·AI Hub를 조사했으나 최종 첫 학습에 사용한 세 출처는 아래 AI Hub 데이터다.
2. 현미경 피부와 얼굴 전체, 두피 확대 영상은 촬영 방식과 보이는 특징이 달라 전문 분류기를 분리했다.
3. 원천 클래스를 직접 살펴 분류할 범위를 골랐다. 이후 원본 Train과 원본+증강 Train을 비교했다. Validation·Test에는 증강을 넣지 않았다.
4. Skin 첫 성능은 높았으나 Web Skin·Hair는 낮았다. 이 점이 2차 데이터 검사와 학습법 변경으로 이어졌다.

|---|---|---:|---:|---|

**Skin 10종:** 기저세포암, 편평세포암, 보웬병, 광선각화증, 지루각화증, 흑색점, 표피낭종, 사마귀, 피부섬유종, 혈관종. 처음 원천 15종 중 악성흑색종·멜라닌세포모반·피지샘증식증·화농육아종·비립종은 미선택이다. 이미지를 직접 검수하며 시각적으로 비슷한 항목을 제외했다는 당시 판단이 기록되어 있다. 다만 **클래스별 제외 판정표나 각 1,000장 중 학습에 쓰지 않은 100장의 개별 사유는 남아 있지 않다.**

**Hair 5종:** 모낭사이홍반, 미세각질, 비듬, 탈모, 피지과다. 중등도·중증 증상을 중심으로 선별하고 적은 클래스인 비듬 2,900장에 맞춰 수량을 균형화했다. 모낭홍반/농포는 모낭사이홍반과 시각적으로 유사하다고 판단해 제외했다. 2026-09-28의 6클래스 `양호`는 이 초기 단계에 포함되지 않는다.

**Web Skin 5종(후속 첫 학습):** 건선, 아토피, 여드름, 정상, 주사. 정면 얼굴 기준으로 선택했다. 지루성 피부염은 주사와 구분이 어렵다는 검토 후 제외했다. 초기 데이터 선별 그림을 발표할 때는 아직 Web Skin을 학습하지 않았다는 시간 순서를 지킨다.

### 분할과 증강을 실제 어떻게 했나

| 도메인 | 첫 원본 Train / Val / Test | 증강 Train | 구현된 증강 |
|---|---|---:|---|
| Skin | 7,300 / 1,000 / 700 | 실행 버전에 따라 클래스당 원본 730장에 생성 470장을 더한 1,200장 또는 별도 전처리의 730장 추가안이 기록됨. **서로 다른 버전을 한 수치로 합치지 않는다.** | 좌우 반전·회전·밝기·대비·화이트밸런스·감마·가우시안/모션 블러·노이즈·JPEG 압축·원근 변형 중 무작위 선택 |
| Web Skin | 3,600 / 500 / 400 | 원본 3,600 + 생성 3,600 = 7,200 | 좌우 반전, 회전, 밝기·대비·채도·색온도, 블러·노이즈, 감마·JPEG, 확대/크롭 중 1~3개를 무작위 조합 |
| Hair | 11,600 / 1,450 / 1,450 | 원본 11,600 + 생성 5,800 = 17,400 | 약한 회전·좌우 반전·밝기/대비/색·블러·노이즈·약한 크롭/확대의 확률적 조합 |

Hair 증강의 구현 예: 회전 ±8°, 밝기 0.82–1.18배, 대비 0.85–1.15배, 색 0.90–1.10배, 약한 crop 0.92–1.0배를 확률적으로 사용했다. 실제 수치는 [초기 Hair 전처리 코드](../scripts/preprocess_hair.py), Skin의 변형 목록은 [Skin 코드](../scripts/preprocess_skin.py), Web Skin의 조합 규칙은 [Web Skin 코드](../scripts/preprocess_web_skin.py)에 있다. 증강의 목적은 조명·초점·자세 변화에 대한 일반화 가능성을 시험하는 것이었다. **증강 이미지 수는 독립 인물 수가 아니다.**

첫 학습은 ImageNet 사전학습 EfficientNet-B0를 가져와 특징 추출부를 고정하고 분류층을 학습했다. 원본 학습과 증강 학습을 비교하면서 Validation 최고 가중치를 보존했다. Skin은 초기 약 99% 수준으로 보고됐으나 그 숫자만으로 실제 현미경 촬영 성능을 보장할 수 없었다. Web Skin 초기 결과는 Validation 최고 66.80%, Test 78.50%, Hair 5종 초기 결과는 원본 Test 68.41%, 증강 Test 69.10%였다. 이 숫자는 **정제 전의 각 초기 평가 기록**이며 Clean 데이터 결과와 직접 상승률을 계산하지 않는다.

당시 YOLO로 병변을 찾아 잘라낸 뒤 Skin 분류기에 넣는 안도 검토했지만, 질환이 넓게 분포하거나 병변 경계가 일정하지 않아 단일 crop만으로 표현하기 어렵다고 판단했다. 따라서 확대 피부 Skin과 얼굴 전체 Web Skin을 별도 분류기로 두었다. 이는 분류기 구조를 정한 판단이며 YOLO 검출 성능을 수치 검증했다는 뜻은 아니다.

#### 그림 사용 순서

`시각자료/`의 `initial_skin_hair_data_selection` → `02_initial_data_split` → `03_initial_augmentation_plan` → `04_initial_training_plan` 순서가 자연스럽다. 첫 그림은 **Web Skin 사용 전** 상태를 나타낸다. 뒤에서 Web Skin을 설명할 때는 이 시점 이후 첫 학습으로 전환되었다고 말한다.

첫 학습곡선은 도메인별 한 장으로 합쳤다: [Skin 4곡선](../presentation/1차/시각자료/skin__initial_four_training_curves.png), [Web Skin 4곡선](../presentation/1차/시각자료/web_skin__initial_four_training_curves.png), [Hair 4곡선](../presentation/1차/시각자료/hair__initial_four_training_curves.png). 세 그림 모두 **ImageNet 사전학습 EfficientNet-B0, 입력 224×224, 분류층 학습 15 epoch**를 제목 아래에 명시했다. 각 그림의 윗줄은 원본 Train, 아랫줄은 원본+증강 Train이고, 왼쪽은 Accuracy·오른쪽은 Loss다. 파란색은 Train, 주황색은 Validation이다. **개별 곡선과 혼동행렬 원본은 `results/<도메인>/1_training/`에 보존돼 있으며 발표 폴더에는 통합 그림만 넣었다.** 이 그림은 Clean 데이터 정제 전 결과이므로 2차 이후 곡선과 같은 검증셋의 직접 비교처럼 배치하지 않는다.

### 왜 세 분류기로 나누었나

처음에는 피부와 두피를 하나의 의료 영상 문제로 생각할 수 있었다. 그러나 현미경 피부 사진에서는 병변의 경계·표면·색과 각질 같은 **작은 부위의 특징**이 크고, 웹캠 얼굴 사진에서는 홍반이 퍼진 **위치와 얼굴 전체 분포**가 중요하다. 두피 확대 사진은 모공 주변 홍반, 비듬·미세각질, 피지 반사와 모발 밀도라는 또 다른 특징을 가진다. 그래서 촬영 **장비**와 촬영 **부위**를 함께 기준으로 `skin`(확대 피부), `web_skin`(정면 얼굴), `hair`(확대 두피)의 분류 대상과 클래스 순서를 분리했다. 이 판단은 나중에 팀원 시스템에 모델을 연결할 때도 그대로 유지해야 하는 입력 계약이다.

이 순서는 한 번에 확정되지 않았다. Skin 10종으로 먼저 높은 저장 점수를 얻은 뒤, 웹캠에서 같은 모델을 바로 쓸 수 있는지 검토했다. 병변 검출 후 잘라내는 YOLO 안은 라벨링이 실패·중단됐고, 얼굴 전체에 퍼지는 증상은 작은 사각형 하나로 설명하기 어렵다고 판단했다. 따라서 얼굴 정면 사진 전용 `web_skin`을 별도로 구성했다. Hair에서는 초기 여섯 증상 후보 중 모낭홍반/농포와 모낭사이홍반이 매우 비슷해, 전자를 제외하고 다섯 증상으로 정의했다. **2026-09-28에 추가한 여섯 번째 `양호`는 이때 제외한 모낭홍반/농포와 다른 클래스**다.

### 데이터 선정이 실제로 뜻하는 것

Skin 원천의 15종 약 15,000장과 첫 모델에 사용한 10종 9,000장은 다른 숫자다. 15종 중 10종을 고른 뒤 선택된 각 클래스에서 900장씩 첫 분할에 넣었다. 당시 직접 이미지를 검수해 시각적으로 구분이 어렵다고 본 클래스를 제외했지만, 왜 선택된 각 원천 클래스의 남은 약 100장을 쓰지 않았는지 **사진 단위 선별 기록은 없다**. 따라서 “1만 장을 모두 학습했다”거나 “나머지 100장은 품질 불량이었다”고 말하지 않는다.

Hair 원천의 고유 이미지 101,027건은 다섯 클래스의 합계가 아니다. 한 두피 사진에 여러 증상 라벨이 붙을 수 있어 증상별 원천 건수를 단순 합산하면 안 된다. 프로젝트에서는 중등도·중증 사진을 중심으로 다섯 범주를 고르고, 가장 적은 비듬 후보 2,900장에 맞춰 각 범주를 균형화했다. 이때의 **14,500장**은 중복 정리 전 첫 데이터 구성이다.

Web Skin 원천은 여섯 클래스의 정면·측면 사진이 있었지만, 실제 첫 학습은 **정면 얼굴 다섯 클래스**를 사용했다. 정면과 측면을 모두 넣으면 같은 사람·병변의 두 각도가 서로 다른 분할에 들어갈 수 있는지도 검토해야 했다. 식별 정보가 충분하지 않아 처음에는 정면만 사용한 것이다. 처음 데이터 선정 발표 그림은 Web Skin을 아직 사용하기 전 장면이므로, 이 설명을 시간상 뒤에 놓는다.

### 원본·증강본은 어떻게 만들었나

증강은 학습 도중 매번 새 이미지를 만드는 방식이 아니라 전처리 코드가 변형 이미지를 **파일로 저장하는 오프라인 증강**이었다. 먼저 Train/Validation/Test를 분리하고, 학습용 Train에서만 파생 사진을 만들었다. Validation과 Test가 원본인 까닭은 모델이 새 원본 사진을 구분하는지 같은 기준에서 비교하기 위해서다. 여기서 `Original 모델`은 원본 Train으로 학습한 모델, `Augmented 모델`은 **원본 Train과 새 증강본을 함께** 사용한 모델이다.

| 대상 | 코드에 기록된 생성 방법 | 왜 선택했나 | 해석할 때 주의 |
|---|---|---|---|
| Skin | [전처리 코드](../scripts/preprocess_skin.py)는 좌우반전, ±10° 회전, 밝기 ±25, 대비 0.85–1.15, 화이트밸런스, 감마, 가우시안·모션 블러, 노이즈, JPEG 열화, 약한 원근 변형의 **11가지 중 한 가지**를 무작위 적용한다. | 현미경 조명·촬영 각도·초점·압축 차이의 가능성을 연습시키려 했다. | 당시 서술은 클래스당 730 원본+470 생성=1,200 Train, 현재 코드 기본은 730+730=1,460 Train이다. 첫 모델의 실제 증강본 수는 당시 데이터 manifest가 없어 확정할 수 없다. |
| Web Skin | [전처리 코드](../scripts/preprocess_web_skin.py)는 반전, ±7° 회전, 밝기 0.75–1.25, 대비 0.80–1.20, 채도 0.85–1.15, 색온도, 블러, 약한 노이즈, 감마, JPEG, 1.02–1.08 확대/크롭에서 서로 다른 변형 **1–3개**를 고른다. 선택 개수 가중치는 45%/40%/15%다. | 얼굴 거리·조명·웹캠 압축의 변화를 흉내 내되 얼굴 구조를 지나치게 손상하지 않으려 했다. | 원본 3,600장에 생성 3,600장을 더한 학습 파일 7,200장은 새 사람 7,200명이 아니다. |
| Hair | [전처리 코드](../scripts/preprocess_hair.py)는 ±8° 회전 65%, 반전 25%, 밝기 0.82–1.18 75%, 대비 0.85–1.15 65%, 색 0.90–1.10 35%, 약한 블러·노이즈 각 25%, 크롭 30%를 조합한다. | 모공·각질 신호가 사라지지 않도록 변형을 약하게 두면서 현미경 각도·조명 차이를 연습하려 했다. | 첫 Train 원본 11,600장에 생성 5,800장을 더해 17,400장을 썼다. 뒤의 Clean Hair 증강 규칙과 수량은 별개다. |

이미지에 변형을 줬다고 실제 장비의 모든 환경 차이가 재현되는 것은 아니다. 지나친 crop이나 블러가 오히려 병변 단서를 없앨 수도 있으므로, 이 선택은 당시 가설이며 효과는 **같은 원본 평가 분할에서 비교한 저장 결과**로 판단한다.

### 첫 모델을 어떻게 학습했고 무엇을 얻었나

모델은 일반 사진 특징을 미리 학습한 **ImageNet EfficientNet-B0**에서 출발했다. 특징 추출부를 고정하고 새 클래스 분류층을 학습하는 `head-only` 방식이다. 저장 결과에는 대체로 입력 224×224, 배치 32, 15 epoch가 남아 있다. Skin 과거 코드는 학습률 1e-3, Web Skin/Hair 기록은 1e-4여서 세 도메인의 조건이 모두 같았다고 단정하지 않는다. 각 모델은 마지막 epoch를 무조건 고르지 않고 Validation Accuracy가 가장 높았던 시점의 가중치를 사용했다. [EfficientNet 원논문](https://proceedings.mlr.press/v97/tan19a.html)은 모델 깊이·너비·입력 해상도의 균형을 논의한다. 여기서 그 논문의 의료 성능을 재현했다는 뜻은 아니다.

| 초기 모델 | Validation Accuracy | Test Accuracy | Test Macro F1 | 당시 얻은 결론 |
|---|---:|---:|---:|---|
| Skin Original | `0.9950000047683716` | `0.9942857027053833` | 저장 결과에 없음 | 매우 높게 보고돼 우선 Skin 경로를 유지 |
| Skin Augmented | `0.9950000047683716` | `0.9957143068313599` | 저장 결과에 없음 | 당시 Test 정확도는 높았으나 뒤에 중복을 발견해 최종 근거로 사용하지 않음 |
| Web Skin Original | `0.6679999828338623` | `0.7850000262260437` | `0.7833125866587888` | 얼굴 질환 간 구분 부족 |
| Web Skin Augmented | `0.6880000233650208` | `0.8199999928474426` | `0.8195818185502844` | 증강 쪽이 높았으나 Validation은 낮아 추가 학습법 검토 |
| Hair Original | `0.7062069177627563` | `0.6841379310344827` | `0.6827345904185209` | 작은 두피 특징 구분이 어려움 |
| Hair Augmented | `0.704827606678009` | `0.6910344827586207` | `0.6894861696407794` | Test는 조금 높지만 큰 개선은 아님 |

이 표의 초기 Test는 **정제 전의 옛 사진 분할**에 대한 기록이다. 나중에 Hair·Skin에서 Train과 평가 사이 완전 동일 사진을 발견했다. 따라서 Skin의 거의 100% 숫자도 실제 장비 성능이나 새 환자 성능으로 발표하지 않는다. 초기 데이터 ZIP은 현재 보존되지 않아 그때의 Test 사진으로 초기 여섯 모델을 다시 추론하는 재현도 끝나지 않았다.

### 다음 차수로 넘어간 이유와 발표 문장

단순 증강만으로 Hair와 Web Skin에서 원하는 구분력이 나오지 않았다. Skin의 높은 성능도 **데이터 중복이 없는지** 확인하기 전에는 신뢰성에 의문이 남았다. 그래서 다음 차수에서는 파일명만 보지 않고 실제 이미지 내용을 비교해 분할을 감사하고, 정제된 분할에서 학습 방법을 바꾸기로 했다.

> “처음에는 데이터 원천과 촬영 방식을 조사해 세 분류 문제를 나눴습니다. 원본과 Train 증강을 비교한 첫 모델에서 확대 피부의 저장 점수는 높았지만 얼굴·두피 분류는 낮았습니다. 그래서 다음 단계에서 분할 중복을 확인하고, 같은 기준으로 다시 학습했습니다.”

## 2. 데이터 검증과 전이학습 최적화

> 1차의 성능 숫자만 올리는 것이 아니라, **평가를 믿을 수 있게 만들고 개선 원인을 분리해서 확인**한 단계다. GitHub 저장소 연결·추론 규칙 정리, 데이터 감사, Clean 분할, 2단계 전이학습, 해상도·손실함수·Backbone 비교가 이어졌다. 세부 실험은 [실험표 CSV](../presentation/2차/최적화_실험표.csv)와 원본 JSON·CSV에서도 확인할 수 있다.

### 왜 다시 시작했나

초기 Hair·Web Skin 성능이 기대보다 낮았다. 먼저 사진 중복과 평가 분할을 점검했다. 같은 사진이 Train과 Validation/Test에 동시에 있으면 모델의 일반화 점수가 과대평가될 수 있다. 그 뒤 데이터 분할을 고정하고 학습법을 한 조건씩 바꿔 효과를 살폈다.

초기 자료를 GitHub 저장소에 연결한 뒤에는 모델·클래스 순서·전처리·평가 코드를 협업 가능한 형태로 정리했다. 저장된 EfficientNet에는 내부 `Rescaling(1/255)`이 있어 추론 코드의 외부 `/255`를 제거했고, 개인 PC 고정 경로와 기존 출력 자동 삭제도 수정했다. **이는 모델 재학습이 아니라 재현·전달 기반을 만드는 작업**이었다. 기존 문서 [GitHub 연결 단계 정리](presentations/1차.md)의 ‘1차’는 이 폴더의 **GitHub 연결 전 1차**와 시기 이름이 다르므로 혼동하지 않는다.

### 데이터 검사·재구성

| 대상 | 확인된 사실 | 조치 | 최종 원본 분할 |
|---|---|---|---|
| Hair | 초기 Original의 완전 동일 이미지 교차 분할 쌍: Train–Val **195**, Train–Test **178**, Val–Test **16**. 이는 **쌍 수**이며 389장 삭제를 의미하지 않는다. 라벨 충돌도 감사했다. | 완전 동일 사진과 증강본의 원본 연결을 기준으로 새 Clean 5종 분할 생성. 증강은 Train에만 적용. | Train 10,032 / Val 1,252 / Test 1,252 = 12,536 |
| Skin | 완전 동일 중복 이미지 **51장** 확인 | Clean 데이터로 재구성 | Train 7,249 / Val 1,000 / Test 700 = 8,949 |
| Web Skin | 사용한 검사에서 교차 분할 완전 동일 바이트·픽셀 사진 미발견 | 기존 분할 유지 | Train 원본 3,600 / Val 500 / Test 400 |

Hair Clean 증강 Train은 원본 10,032장 + 생성 5,015장 = **15,047장**이다. Web Skin 증강 Train은 **7,200장**이다. Skin의 Clean 후 증강 비교는 원본과 같은 Val/Test를 사용했다. 바이트·픽셀 완전 동일 검사는 **유사 사진·같은 사람·같은 병변·같은 촬영 세션의 중복이 없다는 증명은 아니다.** 식별자가 없는 영역은 미검증으로 남겼다. Clean 전후 Test가 달라서 초기 점수와 Clean 점수를 하나의 인과적 개선률로 표현하지 않는다.

### 왜 이런 학습법을 시험했나

| 순서 | 고정한 것 | 바꾼 것과 이유 | 확인된 결과 |
|---|---|---|---|
| 2단계 학습 | Clean 분할, 분류 대상, seed 42 등 | ImageNet EfficientNet의 분류층만 **15 epoch** 학습한 뒤 후반부 **30층 중 BatchNorm 제외** 부분을 작은 학습률로 **10 epoch** 미세조정. 일반 이미지 특징을 우리 사진에 맞게 적응시키려는 [전이학습 절차](https://keras.io/guides/transfer_learning/). | Web Skin B0·256에서 Stage1 최고 Val Accuracy **0.7039999961853027**, Stage2 최고 **0.7960000038146973**. 추가 epoch와 학습률 변경도 동반되므로 미세조정 한 변수만의 순수 효과는 아님. |
| 224→256 | B0, CE, 데이터·학습 절차 | 작은 질감이 리사이즈 중 덜 소실되는지 시험. | Hair Val Accuracy **0.7643769979476929→0.7699680328369141**. Web Skin **0.794→0.796**(500장 중 한 장 차이); Web Skin Macro F1은 거의 동률이라 256의 보편적 우위를 주장하지 않음. |
| CE→Label Smoothing 0.05 | B0·256 등 | 비슷한 질환 사이 과도한 정답 확신을 완화하는 [라벨 스무딩 아이디어](https://openaccess.thecvf.com/content_cvpr_2016/html/Szegedy_Rethinking_the_Inception_CVPR_2016_paper.html). | Hair Val **0.7699680328369141→0.7739616632461548**. Web Skin **0.796→0.794**, 개선 없음. |
| CE→Focal gamma 1.5 | B0·256 등 | 어려운 예의 상대적 손실 비중을 키우는 [Focal Loss](https://openaccess.thecvf.com/content_iccv_2017/html/Lin_Focal_Loss_for_ICCV_2017_paper.html). | Hair Val은 CE보다 낮았고 Web Skin도 **0.796→0.792**. Hair Test가 일부 높은 것은 후보를 다시 고를 이유로 사용하지 않음. 서로 다른 Loss의 숫자 크기는 직접 비교하지 않음. |
| B0→B1 | 256, LS 0.05 등 | [EfficientNet](https://proceedings.mlr.press/v97/tan19a.html) 계열의 더 큰 특징 표현이 도움이 되는지 시험. | Hair Val **0.7739616632461548→0.7763578295707703**, Web Skin **0.794→0.796**. 모델 크기 확대만으로 큰 이득은 확인되지 않음. |
| Hair Stage2 +5 epoch | 같은 Hair B1·256·LS 체크포인트 | Validation 경향을 보고 미세조정 10→15 epoch 연장. | Hair Val **0.7771565318107605**, Test Accuracy **0.7883386581469649**, Macro F1 **0.7885764577048346**. 5종 v1 후보 선정. |

해상도·Loss·Backbone 비교는 각 비교의 분할과 기본 설정을 맞춰 검토했지만, 서로 다른 실험 묶음의 절대 점수 차이를 단일 원인으로 단정하지 않는다. 특히 B1 변경은 파라미터 수도 함께 바뀐다. Hair의 가장 높은 Test 점수를 사후 기준으로 후보를 바꾸지 않고 Validation에서 정한 후보를 보존했다.

### 저장소를 먼저 정리한 이유

초기에는 도메인별로 학습 파일과 모델이 따로 있었고, 저장 모델을 팀원이 정확히 불러오는 규칙도 분명하지 않았다. 저장된 EfficientNet 안에는 픽셀 값을 255로 나누는 층이 이미 있는데 기존 팀 안내 코드가 외부에서 다시 `/255`를 하면 **학습과 다른 입력**이 된다. 그래서 RGB `float32` 0–255를 입력하고 클래스 배열 순서를 보존하는 추론·평가 계약을 정리했다. 전처리 스크립트의 개인 PC 경로와 기존 출력 폴더 자동 삭제도 바로잡아 재현 가능한 실행 기반을 만들었다. 이것은 **모델을 새로 학습한 결과가 아니라** 그 뒤의 실험이 같은 의미로 비교되도록 돕는 코드 정리다. [당시 정리 보고서](presentations/1차.md)에는 이 과정을 상세히 적었다.

### 데이터 감사: 무엇을 검사했고 무엇을 못 검사했나

데이터 누수는 학습에서 본 것과 동일하거나 매우 비슷한 사진이 평가에 들어가 점수가 좋아 보이는 문제다. 파일명이 달라도 사진 내용은 같을 수 있으므로 기존 감사에서 파일 바이트와 디코딩한 RGB 픽셀 기준의 해시를 비교했다. Hair 초기 Original의 Train–Val 195, Train–Test 178, Val–Test 16은 **교차 분할 중복 쌍 수**다. 동일 사진이 셋 이상의 분할에 있는 경우 여러 쌍으로 셀 수 있어 이를 더해 ‘삭제한 389장’이라고 설명하면 틀리다. 서로 다른 클래스에 붙은 동일 사진의 라벨 충돌도 문제였다.

Hair에서는 원본을 다시 모으고 완전 동일 이미지·라벨 충돌을 정리해 12,536장으로 만들었다. 분할을 다시 정한 뒤 **Train 원본 10,032장에만** 새 증강 이미지 5,015장을 만들고 원본–증강 연결을 manifest로 기록했다. 기존 증강본을 그대로 복사해 쓰지 않은 이유는 원본이 새 Validation/Test에 들어간 파생 이미지가 Train에 남으면 누수가 다시 생길 수 있기 때문이다. 초기에 고른 14,500장과 Clean 원본 12,536장의 차이는 1,964장이지만, 이것도 교차 중복 쌍 합계로 설명할 수 없다.

Skin에서는 Train–Val 10그룹, Train–Test 5그룹, Val–Test 1그룹의 완전 동일 RGB 중복이 확인됐다. Train 내부의 중복 그룹·초과 복사본도 있었고, 과거 증강 Train 안에서도 같은 사진의 반복이 발견됐다. 원본 9,000장에서 51장을 정리해 8,949장으로 만들고, Clean Train 7,249장 각각에 새 증강본 한 장을 만들어 **증강 Train 14,498장**으로 구성했다. 생성된 새 증강본의 픽셀 해시 중복·라벨 충돌 검사 기록은 0이었다. [Skin 감사 보고서](research/SKIN_DATA_AUDIT_20260909.md)에 검사 범위가 남아 있다.

Web Skin의 당시 감사에서는 읽을 수 없는 이미지, 완전 동일 파일·RGB 사진의 교차 분할 중복, 라벨 충돌을 발견하지 못해 기존 원본 분할을 유지했다. 그러나 어느 도메인이든 사람 ID·병변 ID·촬영 세션 ID가 충분하지 않았다. **같은 사람이 다른 각도에서 찍힌 사진, 연속 촬영 이미지, crop이나 재압축된 근사 중복까지 없다고 증명한 것은 아니다.** 이후의 공개 데이터 점수는 이 제한을 동반한다.

### 왜 기존 질환 모델에서 이어 학습하지 않았나

특히 Hair에서는 초기 학습 당시 본 사진 일부가 새 Clean Validation/Test에 들어갔을 가능성이 있었다. 그 모델을 출발점으로 삼으면 새 분할에서의 공정한 평가 목적이 약해진다. 또한 모델마다 기존 학습 이력이 다르면 해상도·Loss·Backbone의 효과를 비교하기 어렵다. 그래서 **ImageNet에서 출발하는 새 EfficientNet**으로 각 실험을 시작했다. 같은 EfficientNet-B0라는 구조라도 ImageNet 가중치와 과거 Hair 분류 가중치는 학습 이력이 다른 모델이다.

### 2단계 학습을 쉽게 설명하면

Stage 1에서는 일반 사진에서 배운 특징 추출부를 고정하고 `GlobalAveragePooling → Dropout(0.3) → Dense(클래스 수)` 형태의 새 분류층을 15 epoch 학습했다. Stage 2에서는 Stage 1의 Validation 최고 체크포인트를 불러와 본체 후반 30층 중 BatchNormalization을 제외한 부분만 열고, 학습률을 `1e-4`에서 `1e-5`로 낮춰 10 epoch를 더 학습했다. Hair의 마지막 선정 실험에서는 Stage 2를 5 epoch 더 연장했다. 분류층을 먼저 안정화한 다음 일부 특징을 낮은 학습률로 조정하는 취지는 [Keras의 전이학습·미세조정 지침](https://keras.io/guides/transfer_learning/)과 일치한다.

왜 후반부만 여는가? 처음부터 전체 본체를 크게 변경하면 사전학습에서 얻은 유용한 경계·색·형태 특징이 급히 변할 수 있어서다. 왜 BatchNormalization을 고정하는가? 작은 배치의 통계 변동으로 추론 행동이 흔들리는 일을 줄이려는 설정이었다. Stage 2의 성능 상승에는 **학습 가능한 층 증가뿐 아니라 추가 학습량·낮은 학습률·새 optimizer**가 함께 들어가므로 “30층을 풀기만 해서 오른 점수”라고 말하지 않는다. Web Skin B0·256에서 Stage 1 최고 Validation Accuracy `0.7039999961853027`, Stage 2 최고 `0.7960000038146973`이 이 묶음 절차의 효과를 보여준다.

모든 저장 EfficientNet 후보의 입력은 RGB `float32` 0–255다. 크기에 맞게 TensorFlow bilinear로 리사이즈하고 외부 `/255`를 적용하지 않는다. seed 42, batch 32, 동일 클래스 순서와 데이터 버전을 기록했고, 각 실험에서 Validation Accuracy 최고 체크포인트를 보존했다.

### 각 방법에서 왜 그 변수만 바꿨나

**224→256**은 작은 각질·모공·얼굴 질감이 축소로 소실되는지 묻는 실험이었다. 같은 B0·CE와 분할을 유지했다. Hair Validation은 `0.7643769979476929`에서 `0.7699680328369141`로 올랐지만 Web Skin은 `0.794`에서 `0.796`으로 500장 중 정답 한 장 차이였다. Web Skin의 Macro F1은 오히려 B0·224 `0.7917009497301795`, B0·256 `0.7915394647566528`로 거의 같았다. 큰 입력이 모든 과제에서 이득이라고 결론내리지 않았다.

**Label Smoothing 0.05**는 정답 클래스에 1.0을 몰아주는 학습을 완화하는 방법이다. [Inception 연구](https://openaccess.thecvf.com/content_cvpr_2016/html/Szegedy_Rethinking_the_Inception_CVPR_2016_paper.html)를 참고해 비슷한 클래스 사이의 과신을 줄일 수 있는지 시험했다. B0·256을 고정했을 때 Hair Validation은 `0.7699680328369141`→`0.7739616632461548`로 올랐고 Web Skin은 `0.796`→`0.794`로 내려갔다. 따라서 라벨 스무딩은 항상 좋아지는 스위치가 아니다. 점수가 덜 극단적으로 나왔다고 실제 정답 확률로 잘 보정됐다는 뜻도 아니다.

**Focal Loss gamma 1.5**는 쉬운 예보다 어려운 예의 손실을 상대적으로 크게 남기는 [원 논문](https://openaccess.thecvf.com/content_iccv_2017/html/Lin_Focal_Loss_for_ICCV_2017_paper.html)의 아이디어를 분류에 응용한 것이다. 원 논문은 dense detection을 다뤘고 우리 과제의 클래스 불균형 자체가 주된 이유는 아니었다. Hair의 비슷한 두피 상태가 더 잘 구분되는지 검토했으나 Validation은 CE보다 낮았다. Hair Focal의 Test는 높았지만 Test를 보고 선정 규칙을 바꾸지 않았다. 서로 다른 Loss 함수의 숫자값 자체는 같은 척도로 비교하지 않는다.

**B0→B1**은 더 큰 모델 용량이 세밀한 특징을 표현할 수 있는지 확인했다. 이때 입력 256과 LS 0.05는 유지했지만 구조·파라미터 수가 함께 바뀌었다. Hair Validation Accuracy는 B0 `0.7739616632461548`에서 B1 `0.7763578295707703`으로 소폭 상승했다. Web Skin은 B0 LS `0.794`, B1 LS `0.796`이었다. B1이 무조건 배포에 더 낫다고 볼 정도의 큰 차이는 아니었다.

**Hair B1의 Stage 2 +5 epoch**는 Validation이 계속 개선되는지 확인한 연장 실험이다. 부모 모델 최고 `0.7763578295707703`, 연장 후 최고 `0.7771565318107605`로 차이가 작았다. 같은 모델의 미세조정을 연장했지 새 데이터셋이나 새 클래스의 모델이 아니다. Web Skin B1의 같은 5 epoch 연장은 부모 최고 `0.796`을 넘지 못했다.

### 세 도메인은 어떻게 선정했나

Hair에서는 여섯 설정 중 **Validation Accuracy가 가장 높은** B1·256·LS 0.05·Stage2 총 15 epoch를 v1으로 고정했다. Test 1,252장에서 Accuracy `0.7883386581469649`, Macro F1 `0.7885764577048346`이었다. Focal의 Test 수치가 이 묶음에서 약간 더 좋았더라도 Test를 선정 기준으로 바꾸지 않았다. 다만 탐색 과정에서 Hair의 여러 Test가 이미 확인됐다는 점은 완전히 봉인된 독립 최종 Test보다 근거력이 약하다는 제한이다.

Web Skin은 B0·256·CE와 B1·256·LS가 Validation Accuracy `0.796` 동률이었다. B1의 Macro F1이 `0.7931535064807589`로 B0의 `0.7915394647566528`보다 높았지만 당시 규칙은 **Accuracy 우선, 동률이면 앞선 실험 유지**라 B0를 v1으로 선정했다. Test 400장에서 Accuracy `0.8825`, Macro F1 `0.8813822927981046`이었다. B1 연장 실험을 새 후보로 세지 않은 이유도 부모 최고를 넘지 못했기 때문이다.

Skin은 이미 높은 저장 점수가 있었기 때문에 Hair·Web Skin의 여섯 설정을 그대로 반복하지 않았다. Clean 데이터에서 **B0·224·CE·head-only 15 epoch**를 고정하고 Train 종류만 원본 7,249장과 원본+증강 14,498장으로 비교했다. Validation Accuracy는 `0.973` 대 `0.982`, Macro F1은 `0.9730455448862949` 대 `0.9820008885656606`이었다. 증강 후보를 고정한 뒤 Test 700장에서 Accuracy `0.9871428571428571`, Macro F1 `0.9871314132317626`, 정답 **691장**을 확인하고 v1으로 패키징했다. Test가 초기 약 99.6%보다 낮더라도 평가 사진과 정제 정도가 바뀌었으므로 단순한 성능 악화가 아니다.

### 그림에서 무엇을 읽고, 무엇은 읽지 말아야 하나

감사 그림은 데이터 버전이 왜 바뀌었는지 설명한다. 세 도메인의 학습곡선에서는 파란/주황 선이 Train/Validation, 세로 경계가 head-only에서 부분 미세조정으로 넘어가는 시점을 나타낸다. 그래프가 오른다고 항상 일반화가 좋아진 것은 아니므로 Validation 선과 오차/혼동행렬을 함께 본다. 후보 대시보드는 **2차 당시 선택**을 보여주므로 3차 논문 강화 이후 최신 Web Skin·Hair 후보를 설명할 때는 3차 자료로 넘어간다.

> “먼저 같은 사진이 학습과 평가에 섞이지 않았는지 검사했습니다. Hair와 Skin은 정제한 뒤 일반 영상 사전학습 모델을 같은 분할에서 다시 시작했습니다. 학습층 일부를 조정하고 해상도·Loss·모델 크기를 차례로 시험해 Skin v1, Web Skin v1, Hair 5종 v1을 선정했습니다. 향상 여부는 그때의 Validation 기준으로 판단했습니다.”

## 3. 논문 기반 방법 선별과 v2 후보

> 이 차수는 “논문에서 좋았으니 우리 모델도 좋아졌다”는 이야기가 아니다. **기존 분류기의 어떤 오류를 줄일지 가설을 세우고**, 논문 아이디어를 현재 코드에 맞게 구현한 뒤 **같은 도메인의 Validation**에서 확인했다. 성공·실패 실험을 모두 남기고, 선택한 후보만 Test로 최종 평가했다. 피부 현미경 `skin` 10종은 2차 v1을 유지해 이 차수의 새 모델로 세지 않는다.

### 연구 질문과 평가 원칙

2차 후에도 Hair의 비듬·미세각질처럼 닮은 표면 질감, Web Skin의 아토피·여드름·건선 같은 얼굴 질환 혼동이 남았다. Hair와 Web Skin을 **서로 다른 사진 과제**로 보고 맞는 가설을 따로 시험했다. 같은 도메인 안에서는 Clean 데이터와 Validation을 기준으로 비교하고, Test는 선택한 후보의 최종 평가에만 썼다. 논문은 **방법의 근거**이지 논문 벤치마크 성능을 우리 데이터에 보증하는 자료가 아니다.

해상도 확대 가설은 EfficientNet의 입력 크기 설계와 [피부 병변 다중 해상도 연구](https://pmc.ncbi.nlm.nih.gov/articles/PMC7150512/)를 참고했다. MediFlow는 해당 논문의 앙상블을 그대로 재현한 것이 아니라 **작은 특징 보존이라는 연구 질문**을 B1·384 후보로 시험했다. [실험 CSV](../presentation/3차/논문_실험표.csv)는 원본 결과 JSON의 수치를 담는다.

### 먼저 실험 기준을 어떻게 잡았나

Hair는 정제한 같은 5종 데이터에서, Web Skin은 확인된 같은 얼굴 5종 데이터에서 비교했다. Validation은 방법과 체크포인트를 고르는 데 사용하고 Test는 최종 후보를 고정한 뒤 평가했다. Hair의 SupCon 비교에는 **같은 시기·같은 코드의 B1·256 분류 기준선**을 함께 학습했다. 기존 v1의 숫자만 가져오면 데이터 버전은 같아도 학습 구현·실행 시점의 차이가 섞일 수 있기 때문이다. 이 새 기준선은 ‘새로운 공개 후보’가 아니라 SupCon 효과를 공정하게 읽기 위한 대조군이다.

Hair의 새 기준선 Val Accuracy `0.7755591054313099`, Macro F1 `0.7746028470442391`과 Web Skin 기존 B0·256·CE 기준선 Val Accuracy `0.796`, Macro F1 `0.7915394647566528`을 출발점으로 놓았다. Web Skin 기준선은 이미 저장된 같은 데이터 해시 결과를 재사용했으며 이번 세 방법 실행에서 새로 학습하지 않았다. 이처럼 **새 측정과 과거 저장 결과**를 구분해야 비교표의 의미가 정확하다.

### Hair: 각각 무엇을 보고 왜 시험했나

#### 1. SupCon — 비슷한 두피 클래스의 특징 거리

[Supervised Contrastive Learning](https://papers.neurips.cc/paper_files/paper/2020/hash/d89a66c7c80a29b1bdbab0f2a1a94af8-Abstract.html)은 정답 라벨을 이용해 같은 클래스의 특징 표현은 가깝게, 다른 클래스는 멀게 배치한다. Hair에서 특히 **미세각질과 비듬**은 RGB 사진만 보면 둘 다 하얀 조각 패턴을 보일 수 있었다. 분류층의 경계만 조정하는 대신, 사진이 놓이는 **특징 공간 자체**를 분리해 보면 도움이 될 것이라는 가설이었다.

우리 구현은 B1·256에서 사진의 두 view를 사용한 표현 학습 15 epoch 뒤 분류기를 15 epoch 학습했다. 같은 기준선과 비교한 SupCon Val Accuracy `0.7915335463258786`, Macro F1 `0.7910880666407202`로 기준선 Macro F1 `0.7746028470442391`보다 높았다. 다섯 클래스 F1이 모두 상승했고 미세각질↔비듬 양방향 혼동이 **74→69건**으로 줄었다. 이것은 우리 설정에서 실제 이득이 있었음을 보여준다. 다만 이후 B1·384 단일 모델의 Macro F1 `0.7957146810115047`보다 낮아 최종 공개 후보로 선택하지 않았다. [SupCon 실행 보고서](research/HAIR_SUPCON_RESULT_20260917.md).

#### 2. DINOv2 Small — ImageNet CNN과 다른 사전학습 표현

[DINOv2](https://arxiv.org/abs/2304.07193)는 라벨 없이 대규모 이미지의 범용 시각 표현을 배운다. 기존 ImageNet CNN과 다른 표현이 두피 미세 질감에 유리할지 확인했다. 이 실험에서는 DINOv2 Small 인코더를 **고정**하고 224 입력의 새 선형 분류층만 15 epoch 학습했다. Val Accuracy `0.7699680511182109`, Macro F1 `0.7705341251195019`로 Hair 기준선보다 낮았다. 이는 **224·고정 인코더·Linear Probe** 설정의 결과이며, DINOv2를 미세조정했을 때의 성능이나 다른 의료 데이터에서의 능력을 부정하는 결과가 아니다. [남은 방법 선별 보고서](research/HAIR_REMAINING_METHODS_RESULT_20260917.md).

#### 3. EfficientNetV2-S — 새 CNN 계열의 전이 가능성

[EfficientNetV2](https://proceedings.mlr.press/v139/tan21a.html)는 학습 효율을 고려해 설계된 CNN 계열이다. B1과 다른 구조가 두피에서 더 좋은 특징을 배울지 시험했다. 우리 실험은 입력 256에서 head 학습과 부분 미세조정을 포함했다. Val Accuracy `0.7691693290734825`, Macro F1 `0.7681559382466019`로 기준선보다 낮아 미채택했다. 논문의 일반적인 효율 주장과 **이 Colab 실행에서의 Hair 검증 점수**는 서로 다른 주장이다.

#### 4. B1·384 — 작은 각질 신호를 덜 축소하기

2차에서 B0 224→256은 Hair에 유리했지만 B0→B1만으로 큰 이득이 나오지 않았다. 그래서 “더 큰 본체”보다 **입력의 작은 질감 보존**을 핵심 질문으로 삼았다. [EfficientNet의 해상도 설계](https://proceedings.mlr.press/v97/tan19a.html)와 [피부 병변 다중 해상도 연구](https://pubmed.ncbi.nlm.nih.gov/32292713/)는 이 가설을 검토할 이유였다. MediFlow는 해당 피부 병변 논문의 전체 앙상블을 재현하지 않았다.

B1·384·Label Smoothing 0.05·Adam은 Val Accuracy `0.7963258785942492`, Macro F1 `0.7957146810115047`로 단일 모델 선두였다. Test 1,252장에서는 Accuracy `0.8003194888178914`, Macro F1 `0.8002222282821301`이었다. 5종 v1의 같은 Test Accuracy `0.7883386581469649`, F1 `0.7885764577048346`보다 높았다. 하지만 두 모델의 모든 학습 경로가 해상도만 다른 엄격한 단일 변수 실험은 아니므로 **B1·384 조합의 실증 결과**라고 설명한다. Test에서 비듬 F1 `0.75`, 미세각질 F1 `0.7807692308` 수준으로 어려운 클래스가 여전히 남았다. [최종 패키지 분석](research/HAIR_FINAL_CANDIDATE_V2_20260921.md).

#### 5. SAM과 앙상블 — 선두 모델을 더 개선할 수 있는가

[SAM](https://openreview.net/pdf?id=6Tm1mposlrM)은 현재 한 점뿐 아니라 주변 파라미터에서도 손실이 낮은 방향을 찾는다. 데이터가 조금 달라져도 덜 예민할지 B1·384의 Adam과 비교했다. `rho=0.05`를 쓴 SAM의 Val Accuracy는 같은 `0.7963258785942492`, Macro F1은 `0.7954748920799393`으로 Adam보다 낮았다. 미세각질↔비듬 혼동은 **71→68건**으로 감소했지만 다른 클래스 F1이 낮아졌고 계산 경로도 복잡해 최종 후보를 바꾸지 않았다. [SAM 세부 기록](research/HAIR_SAM_RESULT_20260921.md).

앙상블은 SupCon과 B1·384의 softmax 출력을 **1:1 평균**해 오답이 서로 보완되는지 확인했다. 두 모델 중 하나라도 맞힌 Validation 사진은 1,052장이어서 결합 가능성이 있어 보였지만, 실제 평균의 Accuracy `0.7947284345047924`, Macro F1 `0.7942285283566071`은 B1·384 단일보다 낮았다. **최선의 두 모델을 합치면 항상 더 좋아지는 것은 아니다.** 두 모델을 모두 로드해야 하는 비용도 있어 미채택했다. [오답 보완성 기록](research/HAIR_CANDIDATE_COMPLEMENTARITY_20260921.md).

### Web Skin: 얼굴 전체 속 중요한 부분과 환경 차이

#### 1. WS-DAN — 중요한 부위를 자동으로 찾아 확대

[WS-DAN 원논문](https://arxiv.org/abs/1901.09891)은 attention map으로 구분에 유용한 위치를 찾고, 그 위치를 확대하거나 일부를 가리며 학습하는 세밀 분류 방법이다. 얼굴 사진에서 특정 질환의 단서가 눈·입·머리카락 같은 주변이 아니라 피부 부위에 있는지 보려는 가설이었다. 우리 응용 구현은 **attention map 8개**를 만들고 원본·attention 확대 영역의 예측을 결합했다. Val Accuracy `0.764`, Macro F1 `0.7546949301321499`로 기존 B0·256·CE의 `0.796`/`0.7915394647566528`보다 낮았다. 이는 현재 attention 설정과 데이터에서의 결과다. 원논문 기법 전체의 실패로 일반화하지 않았다.

#### 2. PMG — 전체 얼굴과 여러 크기의 국소 질감

[PMG 원논문](https://arxiv.org/abs/2003.03836)은 다양한 크기의 jigsaw 조각을 단계적으로 학습해 세밀한 부분과 전체 특징을 융합한다. 건선·아토피·여드름이 얼굴에서 비슷한 분포를 보여도 피부의 국소 질감과 병변 크기는 다를 수 있다는 가설을 시험했다. 우리 코드는 **8·4·2 격자**의 조각 경로와 전체 경로를 활용했다. 실제 사용에서는 사진을 별도로 네 번 찍지 않고 **원본 얼굴 사진 한 장**을 입력한다. 네 branch의 logits를 **합산한 뒤 softmax**하는 출력 규칙은 패키지 전처리 계약에 들어 있다.

PMG B0·256은 Val Accuracy `0.85`, Macro F1 `0.8473279632397033`으로 기준선보다 각각 `+0.054`, `+0.0557884984830505` 높았다. Validation 500장의 오분류는 **102→75장**으로 줄었고 다섯 클래스 F1이 모두 상승했다. 특히 아토피·여드름 개선이 의미 있었다. 선택한 이 모델만 Test 400장에서 최종 평가해 Accuracy `0.915`, Macro F1 `0.9141049081029712`를 얻고 Web Skin **v2**로 패키징했다. 원 논문과 프로젝트 구현은 완전히 동일하지 않으므로 ‘PMG 아이디어의 응용’이라고 표현한다. [세 방법 비교 보고서](research/WEB_SKIN_PAPER_METHOD_RESULT_20260922.md).

#### 3. MixStyle — 얼굴 사진의 조명·색감 변화

[MixStyle](https://arxiv.org/abs/2104.02008)은 학습 중 feature의 평균·표준편차를 다른 이미지와 섞어 보지 못한 스타일을 간접적으로 만든다. 웹캠·조명·화이트밸런스가 달라도 질환의 형태를 보도록 하려는 가설이었다. 우리 설정은 EfficientNet의 얕은 특징 경로에 `alpha=0.1`, 적용 확률 `0.5`를 사용했다. 추론 시에는 섞는 단계가 없다. Val Accuracy `0.806`, Macro F1 `0.8033767539683495`로 기준선보다 소폭 높았지만 PMG에는 미치지 못했다. 다른 웹캠에서의 강건성은 **실제 장비 사진 없이 확인하지 못했다.**

#### 4. PMG B1·384 — 성능 1위인데 왜 배포 후보가 아닌가

PMG가 유망했으므로 더 큰 backbone과 384 입력을 결합해 작은 단서가 더 잘 보이는지 시험했다. GPU 메모리 때문에 배치 크기 **32→16**도 함께 바뀌었다. 따라서 B0·256과 비교해 B1만의 효과 또는 해상도만의 효과를 따로 계산할 수 없다. Val Accuracy `0.866`, Macro F1 `0.8643216544321994`로 B0·256보다 높아 **연구상 Validation 선두**였다. 그러나 입력 픽셀은 2.25배, 모델 크기와 학습 시간이 증가했다. 이미 후보를 선택하던 때에 실행 비용을 고려해 B0·256을 v2로 고정했고, 뒤의 4차 Colab 측정은 B1·384의 p50 `419.9053944998923 ms`, B0·256의 `304.2439384998943 ms`를 기록해 비용 차이를 구체화했다. 이는 같은 Colab 환경의 지연 비교이지 실제 웹캠 전체 처리 시간은 아니다. [규모 비교 보고서](research/WEB_SKIN_PMG_B1_384_RESULT_20260923.md).

### MedSigLIP: 의료 사전학습 표현을 선별한 이유

ImageNet 기반 EfficientNet과 달리 [MedSigLIP-448 모델 카드](https://developers.google.com/health-ai-developer-foundations/medsiglip/model-card)의 의료 영상 표현이 질환을 더 잘 분리할 가능성을 확인했다. 그러나 모델 전체를 의료 데이터로 미세조정한 실험이 아니다. **영상 인코더를 고정하고 embedding을 추출해 선형 분류층만 학습**한 Linear Probe였다. 두 도메인 모두 원본 Validation에서 결과를 봤고 Test는 열지 않았다. Web Skin은 Augmented Train 7,200장·원본 Validation 500장, Hair는 Augmented Train 15,047장·원본 Validation 1,252장이었다. 선형 분류층 학습은 AdamW 최대 50 epoch 설정이었다.

Web Skin MedSigLIP Accuracy `0.824`, Macro F1 `0.8195774288599683`은 PMG v2 `0.85`/`0.8473279632397033`보다 낮았다. Hair Accuracy `0.7699680511182109`, Macro F1 `0.7687534259685547`도 B1·384 v2보다 낮았다. 일부 혼동은 줄었지만 평균 성능이 개선되지 않아 **두 모델 모두 최종 선정·패키징하지 않았다**. 특히 저장된 작은 선형층 파일만으로는 추론할 수 없다. 실제 사용에는 큰 MedSigLIP 본체와 전처리도 함께 필요하다. 이 실험이 확인한 것은 **고정 특징의 선형 분리 가능성**이며 full fine-tuning의 결과가 아니다.

### 발표에서 결론을 어떻게 말할까

Hair에서는 SupCon의 유사 클래스 표현 분리 이득이 있었지만 최종 단일 후보는 B1·384였다. Web Skin에서는 PMG B0·256이 분류 성능과 실행 비용을 함께 고려한 v2가 됐다. 다른 방법이 낮았다는 사실도 중요한 결과다. 논문을 적용했다는 이유만으로 채택하지 않고 **우리 Validation에서 확인한 효과**로 결정했다. 서로 다른 도메인의 Test 숫자를 더하거나 순위로 놓지 않는다. Skin은 이 단계에 다시 학습하지 않았다는 사실도 구분한다.

> “Hair는 작은 두피 질감을 더 보존하는 입력과 유사 클래스 표현을 따로 시험했고, 384 입력 B1이 최종 선두였습니다. Web Skin은 얼굴의 국소 특징을 여러 크기로 배우는 PMG가 선두였으며, 더 무거운 384 모델 대신 실행 비용을 고려해 B0·256을 전달 후보로 선택했습니다. 모든 결론은 공개 데이터의 해당 Validation·Test에 한정됩니다.”

## 4. Hair `양호` 추가와 실행 비용 측정

> 이 차수는 서로 다른 두 작업이다. 첫째, 기존 Hair 5종에 새 `양호` 사진을 넣어 **새 6종 분류 문제**를 만들고 네 조건을 학습했다. 둘째, 보존된 전체 모델 **34개를 Colab GPU에서 불러와** 같은 방식으로 실행 시간을 쟀다. 두 번째 작업은 새 모델 학습이나 실제 Jetson·USB 현미경 검증이 아니다. 숫자와 그림의 출처를 혼동하지 않도록 나누어 설명한다.

### 6클래스가 왜 별도 과제인가

기존 Hair 5종에는 `양호` 출력이 없어 새 범위의 사진에도 다섯 증상 중 하나를 선택한다. 사용자가 여섯 증상 값이 모두 0이라고 확인한 두피 사진 **534장**을 별도로 확보해 `양호`를 여섯 번째 클래스로 추가했다. 이 모델의 `양호` 예측은 **이 데이터 정의에서의 양호**일 뿐 모든 질환이 없다는 의학적 판정이 아니다. 새 모델은 과거 5종 모델 가중치를 이어 학습한 것이 아니라 ImageNet 사전학습에서 6종 분류층을 새로 학습했다.

파일명이 같아 보이는 약 2,400장 원천을 수작업으로 정리해 534장을 업로드했고, 두 ZIP 사이 완전 동일 바이트/RGB 픽셀 중복 **0건**을 확인했다. 그러나 유사 사진, 같은 사람·촬영 세션의 분할 간 반복은 식별 정보 부족으로 배제하지 못했다. 새 `양호` 파일별 원천 JSON도 없어서 여섯 증상 0 라벨은 사용자 확인에 따른다. 파일명에서 얻은 **105개 ID**를 묶어 새 사진을 Train 428·Val 53·Test 53장으로 분리했다. 기존 5종 Clean 분할은 유지했다.

| 데이터 | Train 원본 | 증강 조건 Train | Validation 원본 | Test 원본 | 합계 원본 |
|---|---:|---:|---:|---:|---:|
| Hair Clean v1, 5종 | 10,032 | 15,047 | 1,252 | 1,252 | 12,536 |
| Hair Clean v2, 6종 | 10,460 | 17,615 | 1,305 | 1,305 | 13,070 |

6종의 증강 Train 17,615장에는 원본 10,460장과 새 파생 7,155장이 있다. 그중 `양호` 파생 이미지가 **2,140장**이다. 같은 사진에서 파생된 장수는 2,140명의 독립 표본이 아니다. Val/Test는 증강하지 않았다.

### 4개 실험 설계와 결과

고정 조건: 같은 6종 ZIP과 분할, 클래스 순서, seed 42, batch 32, ImageNet 초기 가중치, 분류층 15 epoch + 부분 미세조정 15 epoch. 비교 축은 **모델 묶음**(B0·256·CE 또는 B1·384·LS 0.05)과 **Train 종류**(원본/증강)였다. B0와 B1 묶음 간에는 backbone·입력·Loss가 함께 달라져 B1 구조만의 순수 효과로 읽을 수 없다. 같은 묶음 안에서는 증강 여부를 비교할 수 있지만 증강 데이터 수에 따라 클래스 가중치도 바뀌었다.

### ‘하드웨어 검증’의 실제 범위: Colab GPU 런타임

보존된 모델 **34개/34개**를 Colab GPU에서 실제 로드해 실행 시간을 측정했다. 구성은 Skin 4, Web Skin 12, Hair 5종 14, Hair 6종 4개다. 입력은 **합성 512×512 RGB 한 장**이고 배치 1, 워밍업 10회·반복 30회로 기록했다. `end_to_end_p50`은 이미지 변환과 모델 추론을 포함하지만 모델 로드·카메라 촬영·파일 읽기·네트워크·전체 앱 흐름은 포함하지 않는다. GPU 제품명, 최대 메모리, 전력 측정값도 없다. 따라서 이 장은 **Colab 기준 실행 비용 사전 비교**이며 Jetson/실제 USB 장비에서의 검증으로 발표하면 안 된다.

| 현재 공개 데이터 후보 | Test Macro F1 | Colab end-to-end p50 | p95 | 모델 크기 |

표에서 **같은 Hair 6종 Test**로 비교하면 경량 대안은 성능 우선 대비 Test Macro F1이 약 **0.70%p** 낮고 Colab p50은 약 **121.094 ms 짧다**. 이는 해당 Colab 환경에서의 교환 관계다. Skin/Web Skin/Hair 사이의 정확도 우열을 뜻하지 않는다. 과거 실험의 `training_time`은 서로 다른 실행 기록이므로 이 동일 반복 측정의 추론 시간과 구분한다.

### 새 `양호` 데이터는 어떻게 확인했나

처음 손으로 모은 `양호` 후보는 약 2,400장으로 생각됐지만 파일명이 같은 항목을 정리하고 실제 사진도 확인하면서 최종 업로드 ZIP에는 **534장**이 남았다. 새 사진은 사용자가 **여섯 증상 항목이 모두 0**인 자료라고 확인했다. 그러나 개별 이미지마다 원천 JSON이 있는 상태는 아니므로 보고서에는 “사용자 확인 라벨”이라고 적는다. 같은 파일명이 사람·사진의 모든 중복 기준은 아니어서, 새 ZIP과 기존 Hair Clean v1 ZIP을 다시 교차 검사했다.

검사 결과 JPEG 파일 바이트 완전 일치 **0장**, 이미지를 RGB로 디코딩한 뒤의 픽셀 완전 일치 **0장**이었다. 새 사진 파일명의 첫 숫자 부분은 105개 ID로 묶을 수 있었다. 그러나 기존 12,536장의 파일명은 `탈모_01164.jpg`처럼 새 번호로 정리돼 **12,536장 중 원천 사람 ID를 복구할 수 있는 사진이 0장**이었다. 그래서 감사의 `shared_subject_ids: 0`은 “같은 사람이 0명”이 아니라 **비교할 ID가 없어 판정 불가**라는 뜻이다. 조금 다른 각도·색·압축의 유사 사진도 완전 동일 검사만으로 배제되지 않는다. [양호 교차 감사](research/HAIR_GOOD_CROSS_AUDIT_REVIEW_20260928.md).

분할할 때는 기존 다섯 질환 사진의 Train/Validation/Test 배치를 유지했다. 새 `양호`는 105개 파일명 ID를 묶어 Train **428**, Validation **53**, Test **53**장으로 나눴다. 같은 ID에서 파생된 사진을 새 `양호`의 여러 분할에 섞지 않으려는 설계다. 다만 이 ID가 실제 사람 ID인지 촬영 세션 ID인지는 원천 메타데이터로 독립 확인되지 않았다. 결과적으로 원본 5종 12,536장 + `양호` 534장 = 원본 6종 **13,070장**이 됐다. 이 새 데이터 ZIP은 기존 5종 ZIP을 덮어쓰지 않고 별도로 보관했다.

### 6종 증강은 기존보다 왜 다르게 했나

기존 다섯 질환의 원본 Train은 클래스별 수가 많지만 `양호` Train은 428장뿐이었다. 네 실험에서 원본과 증강 조건을 모두 비교하기 위해, 증강 조건은 기존 다섯 클래스의 Train 원본 약 **50%를 골라 각 한 장**씩 변형하고 `양호`는 원본마다 **5장씩** 파생시켰다. 그래서 생성분 7,155장 중 **2,140장**이 `양호`에서 왔다. 원본 428명 또는 428개 ID가 2,140명의 독립 사례로 늘었다는 뜻이 아니다.

변형은 밝기·대비·색감·±10° 회전·좌우 반전·약한 블러 위주였다. 각 증강본이 어느 원본에서 나왔는지와 적용 설정을 manifest에 남겼다. Validation·Test는 전부 원본이었다. 소수 클래스의 반복을 너무 크게 하면 특정 원본의 색·배경을 외울 위험도 있어, 실제 효과는 같은 Validation에서 **원본 대 증강**으로 확인했다. [네 실험 사전 계약](research/HAIR_SIX_CLASS_FOUR_EXPERIMENTS_PLAN_20260928.md)은 데이터·모델·평가 방법을 고정한 기록이고 [실제 실행 결과](research/HAIR_SIX_CLASS_FOUR_RESULTS_20260928.md)는 그 뒤 완료 상태를 기록한다. 계획 문서의 ‘미실행’ 표기는 작성 당시 상태다.

### 4개 실험은 무엇을 비교했나

기존 Hair v1과 v2를 불러와 여섯 번째 출력만 붙인 것이 아니다. 네 모델은 모두 **ImageNet 가중치에서 새로운 6종 분류층으로** 각각 시작했다. 같은 6종 ZIP·분할·클래스 순서·seed 42·head-only 15 epoch + 후반 30층 부분 미세조정 15 epoch를 공통으로 했다. 실험별 체크포인트는 Validation Accuracy 최고로 저장했고 네 후보의 전체 선택은 **Validation Macro F1, 동률이면 Accuracy** 규칙이었다.

B0·256·CE 안에서 원본과 증강을 비교하면 Validation Macro F1이 `0.7729052037575177`→`0.7819142733310591`이었다. 반면 B1·384·LS 0.05 안에서는 원본 `0.8144942091318823`이 증강 `0.8019837806385383`보다 높았다. 따라서 “증강이 항상 좋다”는 결론을 내리지 않았다. 같은 묶음의 원본/증강 비교라도 **학습 이미지와 그 수량으로 계산한 클래스 가중치가 함께 달라졌다**. B0와 B1끼리의 차이는 backbone·해상도·Loss까지 동시에 달라져 구조 하나의 효과를 분리하지 못한다.

네 실험 중 Val Macro F1이 가장 높은 B1·384·원본을 **성능 우선**으로 골랐다. B0 두 조건 중 Val이 높은 B0·256·증강은 **실행 비용을 비교할 경량 대안**으로 고정했다. 두 모델은 같은 Test 1,305장의 경로와 정답 라벨 집합이 일치했고 각각 후보 패키지의 모델 해시·예측 CSV를 확인했다. 이것은 같은 **6종 과제 안의 두 후보 비교**다. [두 패키지 대조](research/HAIR_SIX_CLASS_LIGHT_HEAVY_COMPARISON_20260928.md).

### Test 결과에서 실제로 무엇을 알았나

성능 우선 B1의 Test Accuracy `0.7915708812260537`, Macro F1 `0.8091500773460419`; 경량 B0의 Accuracy `0.7869731800766283`, Macro F1 `0.8021613486071133`이었다. B1의 6종 Macro F1이 약 **0.70%p** 높지만 두 모델의 입력·Loss·Train 구성도 다르므로 그 차이를 B1 구조의 순수 효과라고 말하지 않는다. `양호` Test 53장 중 **두 모델 모두 49장**을 맞혔다. 다만 다른 질환을 `양호`로 잘못 예측한 사진은 B1 **4장**, B0 **6장**이어서 B1의 `양호` F1이 더 높다.

성능 우선 B1의 클래스별 Test F1은 모낭사이홍반 `0.8187372708757638`, 미세각질 `0.7631578947368421`, 비듬 `0.7284210526315789`, 탈모 `0.8377823408624229`, 피지과다 `0.7822736030828518`, 양호 `0.9245283018867925`다. 특히 비듬 241장 중 **45장**이 미세각질로 분류돼 오랜 난제가 남았다. `양호` 53장은 작고 촬영 환경의 다양성도 충분히 확인되지 않아 현재 점수를 실제 현미경 사용 성능으로 넓히지 않는다.

5종 v2의 전체 Test F1 `0.8002222282821301`과 6종 B1의 `0.8091500773460419`를 빼서 “양호 추가로 성능이 올랐다”고 쓰면 안 된다. 5종 Test는 기존 질환 **1,252장**, 6종 Test는 그 사진에 양호 **53장**을 더했고 출력 클래스도 하나 많다. 동일한 기존 질환 1,252장만 떼어 보면 5종 v2는 **1,002장**, 6종 B1은 **984장**, 6종 B0는 **978장**을 맞혔다. 이 결과는 기존 질환 부분에서 새 6종 모델의 성능이 더 높지 않았다는 분석이다. 그러나 새 `양호` 출력·원본/증강 Train·별도 학습 경로가 함께 달라서 원인을 `양호` 추가 하나로 단정할 수 없다. 이 부분 집합 분석은 **이미 고정된 Test의 사후 설명**이지 Test에 맞춰 후보를 다시 선정한 기록이 아니다.

### 34개 모델 실행 시간: 무엇을 실제 측정했나

Skin **4**, Web Skin **12**, Hair 5종 **14**, Hair 6종 **4**의 저장 모델 총 **34개**를 모두 로드해 실행했다. MedSigLIP 두 조건은 작은 Linear 분류층만이 아니라 **외부 MedSigLIP 영상 인코더까지 포함**해 실행했다. 그러나 `checkpoint_bytes`에는 분류층 파일만 적힌 행이 있으므로 그 용량을 전체 모델 크기라고 해석하면 안 된다. [측정 원자료](../presentation/4차/34개_Colab_실행시간.csv)는 모든 행의 `status=measured`를 보존한다.

환경 기록은 Python 3.13.15·TensorFlow 2.20.0·GPU 1개지만 **GPU 제품명은 기록되지 않았다**. 모델마다 같은 512×512 RGB 상수 이미지를 배치 1로 넣고, 준비 실행 **10회** 후 **30회** 반복했다. `model_p50_ms`는 입력이 준비된 뒤 모델 실행의 중앙값, `end_to_end_p50_ms`는 이번 코드의 이미지 크기 변환부터 출력까지의 중앙값이다. `p95`는 30회 중 느린 쪽 95백분위다. 모델 로드 시간은 `load_seconds`로 별도 기록하고 p50에 넣지 않았다. 카메라 입력, 파일 읽기, 화면·서버, PDF 보고서, 동시 요청, Jetson의 메모리·전력도 포함하지 않았다.

| 지표 | 발표에서 읽는 법 | 이 자료만으로 말할 수 없는 것 |
|---|---|---|
| Validation Accuracy·Macro F1 | 과거 **같은 데이터 분할**의 모델 구분 성능 | 이번 실행에서 새로 재평가한 점수, 다른 도메인 간 우열 |
| Model p50 | 준비된 입력의 모델 계산 중앙값 | 카메라 전체 체감 시간 |
| End-to-end p50·p95 | 이번 이미지 처리 코드의 보통 시간과 느린 쪽 시간 | 장기 안정성, Jetson 실사용 지연 |
| Training seconds | 각 과거 학습 실행에서 걸린 시간 기록 | 34개 모델을 같은 GPU에서 재학습한 공정 속도 순위 |
| Checkpoint bytes·parameter bytes loaded | 파일 크기와 로드된 가중치 크기 | 활성화 메모리를 포함한 최대 RAM/GPU 메모리·전력 |

따라서 이전 안구 발표의 `training time`, `latency`, `trade-off`와 **비슷한 형태의 표는 만들었지만**, 실제 장비에서 측정했다는 뜻은 아니다. 런타임 대시보드의 Accuracy는 **과거 Validation 기록**, 지연 시간만 이번 Colab 실행의 새 측정이다.

### 각 그림을 보면 어떤 판단이 가능한가

Hair 6종의 네 조건은 같은 데이터 버전이므로 `hair6_tradeoff.png`의 위쪽(높은 Validation Accuracy)과 왼쪽(짧은 Colab p50)을 함께 볼 수 있다. B1·384·원본의 Validation Accuracy `0.7992337164750958`·p50 `409.83297050024703 ms`와 B0·256·증강의 `0.7777777777777778`·`288.73898249958074 ms`가 서로 다른 선택을 이끈다. 같은 6종 Test에서도 B1의 Macro F1 `0.8091500773460419`가 B0의 `0.8021613486071133`보다 높았다. 이는 **공개 데이터 분류 성능과 Colab 실행 비용의 교환 관계**다.

Web Skin의 PMG B1·384는 Val Accuracy `0.866`으로 B0·256의 `0.85`보다 높지만 Colab p50은 `419.9053944998923 ms` 대 `304.2439384998943 ms`로 길다. 선택한 Web Skin v2가 비용 균형 후보라는 이유를 수치로 설명할 수 있다. Hair 5종에서 SupCon B1·256의 p50 `398.9703649999683 ms`는 같은 기준선 `399.0923975006808 ms`와 거의 같으면서 Validation Macro F1은 더 높았다. 하지만 최종 B1·384 v2의 Validation 성능이 더 높아 후보는 유지됐다. Skin은 Clean 증강의 Validation Accuracy `0.982`가 Clean 원본 `0.973`보다 높았고, p50은 거의 같았다. **서로 다른 분류기끼리의 Accuracy가 높은 순서**로 모델 기술의 우수성을 평가해서는 안 된다.

`*_metrics_overview.png`의 색 지도는 각 열의 크기를 따로 정규화한다. 진한 색이 반드시 ‘좋음’을 뜻하지 않는다. 오른쪽 상자그림은 한 모델의 30회 변동이 아니라 **한 과제 안의 여러 모델 지연 시간 분포**다. `*_dashboard.png`의 초록 학습 시간 막대는 과거 실행 환경이 다른 기록이다. 초기에 만든 모델과 Clean 모델이 한 그림에 함께 있으면 **분할이 다른 점수는 연결선처럼 읽지 않는다**. 실제 해석은 [런타임 검토 보고서](research/RUNTIME_BENCHMARK_REVIEW_20260928.md)의 그래프 설명을 따른다.

> “새 양호 사진을 검토해 Hair 6종 과제를 만들고 네 조건을 같은 분할에서 비교했습니다. 정확도 우선 B1·384 원본과 실행 비용 대안 B0·256 증강을 별도로 보존했습니다. 이어 저장 모델 34개를 Colab GPU에서 동일한 합성 입력으로 측정해 분류 성능과 실행 시간의 교환 관계를 확인했습니다. 실제 장비·실사용 사진의 성능과 지연 시간은 아직 측정하지 않았습니다.”

## 5. 팀원 저장소, LLM·VLM과 시스템 연결 범위

### 5.1 당시 확인한 키오스크 구조

2026-09-13에 팀원의 [mediflow-kiosk-core 저장소](https://github.com/Phjrab/mediflow-kiosk-core)를 당시 고정 커밋 `2877e65f99bb1a3f9837b56c0736de57a4f66902`에서 검토했다. [검토 원문](research/KIOSK_CORE_REVIEW_20260913.md)은 웹·안구·LLM 코드와 피부·두피 모델을 연결할 위치를 추적한 **코드 분석**이지, 이후의 최신 원격 상태나 실제 장비 실행을 재확인한 기록이 아니다.

당시 안구 경로에는 분류·분석 코드가 있었고 피부·두피는 촬영·표시 화면 중심이었다. 웹의 `skin`은 **얼굴 웹캠 피부**를 뜻했으므로 이 저장소의 `skin`(확대 피부)과 이름을 그대로 대응시키면 잘못된 모델이 호출된다. 두피 화면의 `scalp`는 여기의 `hair`에 해당한다. 확대 피부는 별도 검사 항목을 만들어야 한다. 검사 설정의 피부·두피 `not_configured`를 `ready`로 바꾸기만 해서는 추론이 구현되지 않는다. 당시 웹 업로드 이미지에는 최대 변 1280으로 축소하고 JPEG 재인코딩하는 경로가 있어, 저장된 연구 Test 이미지와 같은 입력이라고 가정할 수도 없다.

### 5.2 모델 전달 계약

사용할 모델 폴더마다 `.keras`, `class_names.json`, `preprocessing.json`, `selection.json`, SHA-256을 함께 전달한다. **배열 출력 순서는 클래스 파일의 순서**로 해석하고, 장비와 촬영 부위를 함께 확인해 라우팅한다. 현재 저장된 EfficientNet 모델은 내부에 `Rescaling(1/255)`이 있으므로 외부에서 한 번 더 `/255` 하지 않는다. Web Skin PMG는 네 분류 출력을 결합하는 전용 추론 규칙이 있으므로 일반 단일 출력 모델처럼 호출하면 안 된다. [선정 모델 경로](../results/SELECTED_MODEL_PATHS.md)와 [모델 사용 계약](../results/MODEL_USAGE.md)이 구현 기준이다.

입력이 흐리거나 사진 종류가 맞지 않거나 모델 범위 밖이라고 의심될 때의 오류·보류 상태는 분류 결과와 따로 표현해야 한다. 모델 최고 점수를 의학적 확률 또는 `정상` 판정으로 바꾸지 않는다. Hair 6종의 `양호`도 확보한 자료 정의에 따른 클래스이며 모든 질환이 없다는 판정은 아니다.

### 5.3 LLM과 VLM은 어디까지 했나

당시 팀원 저장소에는 **텍스트 LLM 채팅 연결**이 있었지만 우리 세 피부·두피 분류기의 구조화 결과를 실제로 연결한 경로는 확인되지 않았다. 이미지와 텍스트를 함께 직접 입력하는 Medical VLM 운영 경로도 확인되지 않았다. MedSigLIP-448 실험은 두 도메인에서 의료 영상 사전학습 **특징 추출기 + Linear 분류층**을 평가한 것이며, 진료 대화를 생성하는 VLM을 구축한 작업이 아니다. 따라서 LLM/VLM과 분류기 결과를 하나의 완성 시스템이라고 발표하지 않는다.

후속 통합을 다시 시작한다면 모델 결과를 `domain`, `model_version`, `class_names`, `predicted_class`, `scores`, `input_quality`, `status`, `timestamp` 등 명시적인 JSON으로 전달하고, LLM에는 검증된 결과만 설명하도록 해야 한다. 사진에서 확인하지 못한 질환·위험도·치료를 만들어내지 않는 규칙과 실제 응답 평가가 필요하다. 화면, 서버, 데이터베이스, 보고서가 동일한 클래스 계약을 사용하는지 통합 테스트해야 한다. **현재 우선순위에서는 장비·LLM·VLM 통합을 보류**하고 있다.

## 6. 무엇이 끝났고 무엇이 끝나지 않았나

현재 공개 데이터에 대해 세 도메인의 원천 조사, 전처리·원본/증강 비교, Hair와 Skin의 완전 동일 중복 정리, 재학습 최적화, Hair·Web Skin의 논문 기반 선별, 각 선정 후보의 Test 평가·패키징, Hair 6종 네 조건과 두 후보 패키징, 저장 모델 34개 Colab 실행 비용 측정까지 기록되어 있다. 발표용 도표와 근거 링크도 [발표 자료실](../presentation/README.md)에 구간별로 모았다. 34개 측정은 Skin 4, Web Skin 12, Hair 5종 14, Hair 6종 4개이며 합성 512×512 RGB 이미지와 배치 1 조건이다.

그럼에도 다음은 **미완료**다. 정제 전 초기 데이터셋이 남아 있지 않아 처음 6개 모델을 당시 Test 이미지로 재추론하지 못했다. Hair 6종 `양호`의 개별 원천 라벨 근거, 같은 사람·촬영 세션 여부, 기존 데이터와의 유사 이미지 겹침은 완전히 검증되지 않았다. 실제 USB 현미경·웹캠 촬영 표본으로 정확도와 실패 유형을 측정하지 않았다. Jetson의 추론 시간·메모리·전력, 카메라에서 결과 화면까지의 지연도 측정하지 않았다. 팀원 저장소의 세 분류기 호출이나 LLM/VLM 운영 연결도 완료하지 않았다. 34개 실행 시간 측정만으로 실제 장비 성능을 주장하지 않는다.

## 7. 앞으로의 계획과 우선순위

### 7.1 현재 정리 작업 직후

이 보고서와 [로드맵](ROADMAP.md), [현재 상태](PROJECT_STATUS_20260928.md), 모델 선정 JSON을 서로 같은 버전으로 관리한다. 발표에서는 초기·Clean·논문·Hair 6종의 **데이터셋과 평가셋이 언제 바뀌었는지**를 먼저 밝힌다. 예전 9월 14일·23일 보고서는 당시 기록으로만 읽고 최신 후보 목록을 덮어쓰지 않는다.

### 7.2 다음 모델 연구: 세 과제별 구조 비교

[로드맵 11단계](ROADMAP.md)의 다음 연구는 Skin 10종, Web Skin 5종, Hair 6종에서 **각각** 여러 경량/중형 분류 구조를 같은 과제 안에서 비교하는 것이다. 과제별 데이터 ZIP·클래스 순서·Train/Validation/Test·평가 코드를 고정하고, 구조별 입력 크기·권장 전처리·필요한 동반 변경은 분리해 기록한다. Validation Accuracy뿐 아니라 Macro F1, 각 클래스의 Recall/F1, 혼동행렬과 모델 크기·속도를 함께 본다. 후보를 Validation으로 고정한 뒤 해당 데이터 버전의 Test를 평가한다. Hair 5종과 6종을 동일 과제의 기준선처럼 직접 뺄 수 없다.

### 7.3 실제 촬영 데이터와 장비 검증

사용 장비와 촬영 부위를 구분해 소규모 익명 데이터의 사람·병변·촬영 세션 ID, 배율, 조명, 거리, 해상도, 날짜와 라벨 근거를 기록한다. 학습에 섞지 않은 검증셋에서 공개 데이터 대비 Accuracy·Macro F1·클래스별 오류를 확인해 **도메인 차이**를 분석한다. Hair `양호` 원천의 증상값 0 확인을 파일별 메타데이터 또는 별도 검토 기록과 대조한다. 유사 사진과 같은 촬영 세션이 서로 다른 분할에 있는지 재검사한다.

최종 장비가 정해지면 실제 카메라 입력→전처리→모델→결과 화면의 p50/p95 지연, 최대 RAM/GPU 메모리, 전력, 안정성을 같은 프로토콜로 측정한다. 기존 Colab 수치는 가설을 좁히는 사전 비교로만 보존한다. 이 단계가 끝나야 장비 탑재 적합성과 실제 입력에서의 성능을 주장할 수 있다. 장비 작업은 현재 사용자 담당 범위에서는 보류되어 있다.

### 7.4 이후 팀 통합

팀과 역할·일정이 정해지면 위의 모델 사용 계약을 기준으로 `web_skin`, `skin`, `hair` 라우터와 오류 상태를 연결한다. 한 검사 결과가 화면·DB·보고서·LLM 설명에 일관되게 전달되는지 테스트한다. Medical VLM은 분류기와 별도 목적·데이터·평가 기준을 마련한 뒤 연구한다. 로봇 제어나 클러스터 구축은 현재 AI 분류 연구의 완료 범위가 아니며 별도 협의가 필요하다.
