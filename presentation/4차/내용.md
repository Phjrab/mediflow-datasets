# 4차 · Hair `양호` 추가와 실행 비용 측정

> 이 차수는 서로 다른 두 작업이다. 첫째, 기존 Hair 5종에 새 `양호` 사진을 넣어 **새 6종 분류 문제**를 만들고 네 조건을 학습했다. 둘째, 보존된 전체 모델 **34개를 Colab GPU에서 불러와** 같은 방식으로 실행 시간을 쟀다. 두 번째 작업은 새 모델 학습이나 실제 Jetson·USB 현미경 검증이 아니다. 숫자와 그림의 출처를 혼동하지 않도록 나누어 설명한다.

## 6클래스가 왜 별도 과제인가

기존 Hair 5종에는 `양호` 출력이 없어 새 범위의 사진에도 다섯 증상 중 하나를 선택한다. 사용자가 여섯 증상 값이 모두 0이라고 확인한 두피 사진 **534장**을 별도로 확보해 `양호`를 여섯 번째 클래스로 추가했다. 이 모델의 `양호` 예측은 **이 데이터 정의에서의 양호**일 뿐 모든 질환이 없다는 의학적 판정이 아니다. 새 모델은 과거 5종 모델 가중치를 이어 학습한 것이 아니라 ImageNet 사전학습에서 6종 분류층을 새로 학습했다.

파일명이 같아 보이는 약 2,400장 원천을 수작업으로 정리해 534장을 업로드했고, 두 ZIP 사이 완전 동일 바이트/RGB 픽셀 중복 **0건**을 확인했다. 그러나 유사 사진, 같은 사람·촬영 세션의 분할 간 반복은 식별 정보 부족으로 배제하지 못했다. 새 `양호` 파일별 원천 JSON도 없어서 여섯 증상 0 라벨은 사용자 확인에 따른다. 파일명에서 얻은 **105개 ID**를 묶어 새 사진을 Train 428·Val 53·Test 53장으로 분리했다. 기존 5종 Clean 분할은 유지했다.

| 데이터 | Train 원본 | 증강 조건 Train | Validation 원본 | Test 원본 | 합계 원본 |
|---|---:|---:|---:|---:|---:|
| Hair Clean v1, 5종 | 10,032 | 15,047 | 1,252 | 1,252 | 12,536 |
| Hair Clean v2, 6종 | 10,460 | 17,615 | 1,305 | 1,305 | 13,070 |

6종의 증강 Train 17,615장에는 원본 10,460장과 새 파생 7,155장이 있다. 그중 `양호` 파생 이미지가 **2,140장**이다. 같은 사진에서 파생된 장수는 2,140명의 독립 표본이 아니다. Val/Test는 증강하지 않았다.

## 4개 실험 설계와 결과

고정 조건: 같은 6종 ZIP과 분할, 클래스 순서, seed 42, batch 32, ImageNet 초기 가중치, 분류층 15 epoch + 부분 미세조정 15 epoch. 비교 축은 **모델 묶음**(B0·256·CE 또는 B1·384·LS 0.05)과 **Train 종류**(원본/증강)였다. B0와 B1 묶음 간에는 backbone·입력·Loss가 함께 달라져 B1 구조만의 순수 효과로 읽을 수 없다. 같은 묶음 안에서는 증강 여부를 비교할 수 있지만 증강 데이터 수에 따라 클래스 가중치도 바뀌었다.

| 실험 | Train 장수 | Val Accuracy | Val Macro F1 | Val `양호` Recall | 학습 기록 시간 |
|---|---:|---:|---:|---:|---:|
| B0·256·CE 원본 | 10,460 | 0.7693486590038314 | 0.7729052037575177 | 0.8867924528301887 | 481.5590983410011초 |
| B0·256·CE 증강 | 17,615 | 0.7777777777777778 | 0.7819142733310591 | 0.8867924528301887 | 652.9102525090002초 |
| **B1·384·LS 0.05 원본** | 10,460 | **0.7992337164750958** | **0.8144942091318823** | **0.9433962264150944** | 1153.4809966860012초 |
| B1·384·LS 0.05 증강 | 17,615 | 0.7931034482758621 | 0.8019837806385383 | 0.9056603773584906 | 1683.8028229350002초 |

B0에서는 증강이 Val Macro F1을 약 0.90%p 높였고, B1 묶음에서는 원본이 증강보다 약 1.25%p 높았다. 이는 해당 실행의 관찰값이며 증강의 일반적 유불리를 뜻하지 않는다. Validation 1위 **B1·384 원본**을 성능 우선으로, 두 B0 중 Validation이 높은 **B0·256 증강**을 작은 실행 비용 대안으로 고정했다. 둘 다 같은 고정 Test 1,305장에서 최종 평가했다.

| 고정된 6종 후보 | Test Accuracy | Test Macro F1 | `양호` F1 | `.keras` 크기 |
|---|---:|---:|---:|---:|
| 성능 우선 B1·384 원본 | **0.7915708812260537** | **0.8091500773460419** | **0.9245283018867925** | 47,234,592 bytes |
| 경량 대안 B0·256 증강 | 0.7869731800766283 | 0.8021613486071133 | 0.9074074074074073 | 29,005,042 bytes |

두 모델 모두 `양호` Test **53장 중 49장**을 맞혔다. 다른 질환을 `양호`로 잘못 예측한 수는 B1 **4장**, B0 **6장**이다. 5종 Test는 1,252장·출력 5개, 6종 Test는 1,305장·출력 6개이므로 전체 Macro F1을 빼서 “클래스 추가가 성능을 개선했다”고 말할 수 없다. 동일한 기존 질환 1,252장 부분만 보면 5종 v2는 **1002장 정답**, 6종 B1은 **984장**, 6종 B0는 **978장**이다. 이 사후 분석도 새 데이터·Train·출력층 등 차이가 있어 저하 원인을 `양호` 추가 하나로 단정하지 않는다.

## ‘하드웨어 검증’의 실제 범위: Colab GPU 런타임

보존된 모델 **34개/34개**를 Colab GPU에서 실제 로드해 실행 시간을 측정했다. 구성은 Skin 4, Web Skin 12, Hair 5종 14, Hair 6종 4개다. 입력은 **합성 512×512 RGB 한 장**이고 배치 1, 워밍업 10회·반복 30회로 기록했다. `end_to_end_p50`은 이미지 변환과 모델 추론을 포함하지만 모델 로드·카메라 촬영·파일 읽기·네트워크·전체 앱 흐름은 포함하지 않는다. GPU 제품명, 최대 메모리, 전력 측정값도 없다. 따라서 이 장은 **Colab 기준 실행 비용 사전 비교**이며 Jetson/실제 USB 장비에서의 검증으로 발표하면 안 된다.

| 현재 공개 데이터 후보 | Test Macro F1 | Colab end-to-end p50 | p95 | 모델 크기 |
|---|---:|---:|---:|---:|
| Skin 10종 v1 B0·224 | 0.9871314132317626 | 282.2758660004183 ms | 287.72185900015756 ms | 17,198,406 bytes |
| Web Skin 5종 v2 PMG B0·256 | 0.9141049081029712 | 304.2439384998943 ms | 308.3123600008548 ms | 36,377,179 bytes |
| Hair 5종 v2 B1·384 | 0.8002222282821301 | 407.29406550008207 ms | 416.95755700038717 ms | 47,219,220 bytes |
| Hair 6종 성능 우선 B1·384 | 0.8091500773460419 | 409.83297050024703 ms | 422.71190300016315 ms | 47,234,592 bytes |
| Hair 6종 경량 B0·256 | 0.8021613486071133 | 288.73898249958074 ms | 296.42769299971405 ms | 29,005,042 bytes |

표에서 **같은 Hair 6종 Test**로 비교하면 경량 대안은 성능 우선 대비 Test Macro F1이 약 **0.70%p** 낮고 Colab p50은 약 **121.094 ms 짧다**. 이는 해당 Colab 환경에서의 교환 관계다. Skin/Web Skin/Hair 사이의 정확도 우열을 뜻하지 않는다. 과거 실험의 `training_time`은 서로 다른 실행 기록이므로 이 동일 반복 측정의 추론 시간과 구분한다.

## 새 `양호` 데이터는 어떻게 확인했나

처음 손으로 모은 `양호` 후보는 약 2,400장으로 생각됐지만 파일명이 같은 항목을 정리하고 실제 사진도 확인하면서 최종 업로드 ZIP에는 **534장**이 남았다. 새 사진은 사용자가 **여섯 증상 항목이 모두 0**인 자료라고 확인했다. 그러나 개별 이미지마다 원천 JSON이 있는 상태는 아니므로 보고서에는 “사용자 확인 라벨”이라고 적는다. 같은 파일명이 사람·사진의 모든 중복 기준은 아니어서, 새 ZIP과 기존 Hair Clean v1 ZIP을 다시 교차 검사했다.

검사 결과 JPEG 파일 바이트 완전 일치 **0장**, 이미지를 RGB로 디코딩한 뒤의 픽셀 완전 일치 **0장**이었다. 새 사진 파일명의 첫 숫자 부분은 105개 ID로 묶을 수 있었다. 그러나 기존 12,536장의 파일명은 `탈모_01164.jpg`처럼 새 번호로 정리돼 **12,536장 중 원천 사람 ID를 복구할 수 있는 사진이 0장**이었다. 그래서 감사의 `shared_subject_ids: 0`은 “같은 사람이 0명”이 아니라 **비교할 ID가 없어 판정 불가**라는 뜻이다. 조금 다른 각도·색·압축의 유사 사진도 완전 동일 검사만으로 배제되지 않는다. [양호 교차 감사](../../docs/research/HAIR_GOOD_CROSS_AUDIT_REVIEW_20260928.md).

분할할 때는 기존 다섯 질환 사진의 Train/Validation/Test 배치를 유지했다. 새 `양호`는 105개 파일명 ID를 묶어 Train **428**, Validation **53**, Test **53**장으로 나눴다. 같은 ID에서 파생된 사진을 새 `양호`의 여러 분할에 섞지 않으려는 설계다. 다만 이 ID가 실제 사람 ID인지 촬영 세션 ID인지는 원천 메타데이터로 독립 확인되지 않았다. 결과적으로 원본 5종 12,536장 + `양호` 534장 = 원본 6종 **13,070장**이 됐다. 이 새 데이터 ZIP은 기존 5종 ZIP을 덮어쓰지 않고 별도로 보관했다.

## 6종 증강은 기존보다 왜 다르게 했나

기존 다섯 질환의 원본 Train은 클래스별 수가 많지만 `양호` Train은 428장뿐이었다. 네 실험에서 원본과 증강 조건을 모두 비교하기 위해, 증강 조건은 기존 다섯 클래스의 Train 원본 약 **50%를 골라 각 한 장**씩 변형하고 `양호`는 원본마다 **5장씩** 파생시켰다. 그래서 생성분 7,155장 중 **2,140장**이 `양호`에서 왔다. 원본 428명 또는 428개 ID가 2,140명의 독립 사례로 늘었다는 뜻이 아니다.

변형은 밝기·대비·색감·±10° 회전·좌우 반전·약한 블러 위주였다. 각 증강본이 어느 원본에서 나왔는지와 적용 설정을 manifest에 남겼다. Validation·Test는 전부 원본이었다. 소수 클래스의 반복을 너무 크게 하면 특정 원본의 색·배경을 외울 위험도 있어, 실제 효과는 같은 Validation에서 **원본 대 증강**으로 확인했다. [네 실험 사전 계약](../../docs/research/HAIR_SIX_CLASS_FOUR_EXPERIMENTS_PLAN_20260928.md)은 데이터·모델·평가 방법을 고정한 기록이고 [실제 실행 결과](../../docs/research/HAIR_SIX_CLASS_FOUR_RESULTS_20260928.md)는 그 뒤 완료 상태를 기록한다. 계획 문서의 ‘미실행’ 표기는 작성 당시 상태다.

## 4개 실험은 무엇을 비교했나

기존 Hair v1과 v2를 불러와 여섯 번째 출력만 붙인 것이 아니다. 네 모델은 모두 **ImageNet 가중치에서 새로운 6종 분류층으로** 각각 시작했다. 같은 6종 ZIP·분할·클래스 순서·seed 42·head-only 15 epoch + 후반 30층 부분 미세조정 15 epoch를 공통으로 했다. 실험별 체크포인트는 Validation Accuracy 최고로 저장했고 네 후보의 전체 선택은 **Validation Macro F1, 동률이면 Accuracy** 규칙이었다.

B0·256·CE 안에서 원본과 증강을 비교하면 Validation Macro F1이 `0.7729052037575177`→`0.7819142733310591`이었다. 반면 B1·384·LS 0.05 안에서는 원본 `0.8144942091318823`이 증강 `0.8019837806385383`보다 높았다. 따라서 “증강이 항상 좋다”는 결론을 내리지 않았다. 같은 묶음의 원본/증강 비교라도 **학습 이미지와 그 수량으로 계산한 클래스 가중치가 함께 달라졌다**. B0와 B1끼리의 차이는 backbone·해상도·Loss까지 동시에 달라져 구조 하나의 효과를 분리하지 못한다.

네 실험 중 Val Macro F1이 가장 높은 B1·384·원본을 **성능 우선**으로 골랐다. B0 두 조건 중 Val이 높은 B0·256·증강은 **실행 비용을 비교할 경량 대안**으로 고정했다. 두 모델은 같은 Test 1,305장의 경로와 정답 라벨 집합이 일치했고 각각 후보 패키지의 모델 해시·예측 CSV를 확인했다. 이것은 같은 **6종 과제 안의 두 후보 비교**다. [두 패키지 대조](../../docs/research/HAIR_SIX_CLASS_LIGHT_HEAVY_COMPARISON_20260928.md).

## Test 결과에서 실제로 무엇을 알았나

성능 우선 B1의 Test Accuracy `0.7915708812260537`, Macro F1 `0.8091500773460419`; 경량 B0의 Accuracy `0.7869731800766283`, Macro F1 `0.8021613486071133`이었다. B1의 6종 Macro F1이 약 **0.70%p** 높지만 두 모델의 입력·Loss·Train 구성도 다르므로 그 차이를 B1 구조의 순수 효과라고 말하지 않는다. `양호` Test 53장 중 **두 모델 모두 49장**을 맞혔다. 다만 다른 질환을 `양호`로 잘못 예측한 사진은 B1 **4장**, B0 **6장**이어서 B1의 `양호` F1이 더 높다.

성능 우선 B1의 클래스별 Test F1은 모낭사이홍반 `0.8187372708757638`, 미세각질 `0.7631578947368421`, 비듬 `0.7284210526315789`, 탈모 `0.8377823408624229`, 피지과다 `0.7822736030828518`, 양호 `0.9245283018867925`다. 특히 비듬 241장 중 **45장**이 미세각질로 분류돼 오랜 난제가 남았다. `양호` 53장은 작고 촬영 환경의 다양성도 충분히 확인되지 않아 현재 점수를 실제 현미경 사용 성능으로 넓히지 않는다.

5종 v2의 전체 Test F1 `0.8002222282821301`과 6종 B1의 `0.8091500773460419`를 빼서 “양호 추가로 성능이 올랐다”고 쓰면 안 된다. 5종 Test는 기존 질환 **1,252장**, 6종 Test는 그 사진에 양호 **53장**을 더했고 출력 클래스도 하나 많다. 동일한 기존 질환 1,252장만 떼어 보면 5종 v2는 **1,002장**, 6종 B1은 **984장**, 6종 B0는 **978장**을 맞혔다. 이 결과는 기존 질환 부분에서 새 6종 모델의 성능이 더 높지 않았다는 분석이다. 그러나 새 `양호` 출력·원본/증강 Train·별도 학습 경로가 함께 달라서 원인을 `양호` 추가 하나로 단정할 수 없다. 이 부분 집합 분석은 **이미 고정된 Test의 사후 설명**이지 Test에 맞춰 후보를 다시 선정한 기록이 아니다.

## 34개 모델 실행 시간: 무엇을 실제 측정했나

Skin **4**, Web Skin **12**, Hair 5종 **14**, Hair 6종 **4**의 저장 모델 총 **34개**를 모두 로드해 실행했다. MedSigLIP 두 조건은 작은 Linear 분류층만이 아니라 **외부 MedSigLIP 영상 인코더까지 포함**해 실행했다. 그러나 `checkpoint_bytes`에는 분류층 파일만 적힌 행이 있으므로 그 용량을 전체 모델 크기라고 해석하면 안 된다. [측정 원자료](34개_Colab_실행시간.csv)는 모든 행의 `status=measured`를 보존한다.

환경 기록은 Python 3.13.15·TensorFlow 2.20.0·GPU 1개지만 **GPU 제품명은 기록되지 않았다**. 모델마다 같은 512×512 RGB 상수 이미지를 배치 1로 넣고, 준비 실행 **10회** 후 **30회** 반복했다. `model_p50_ms`는 입력이 준비된 뒤 모델 실행의 중앙값, `end_to_end_p50_ms`는 이번 코드의 이미지 크기 변환부터 출력까지의 중앙값이다. `p95`는 30회 중 느린 쪽 95백분위다. 모델 로드 시간은 `load_seconds`로 별도 기록하고 p50에 넣지 않았다. 카메라 입력, 파일 읽기, 화면·서버, PDF 보고서, 동시 요청, Jetson의 메모리·전력도 포함하지 않았다.

| 지표 | 발표에서 읽는 법 | 이 자료만으로 말할 수 없는 것 |
|---|---|---|
| Validation Accuracy·Macro F1 | 과거 **같은 데이터 분할**의 모델 구분 성능 | 이번 실행에서 새로 재평가한 점수, 다른 도메인 간 우열 |
| Model p50 | 준비된 입력의 모델 계산 중앙값 | 카메라 전체 체감 시간 |
| End-to-end p50·p95 | 이번 이미지 처리 코드의 보통 시간과 느린 쪽 시간 | 장기 안정성, Jetson 실사용 지연 |
| Training seconds | 각 과거 학습 실행에서 걸린 시간 기록 | 34개 모델을 같은 GPU에서 재학습한 공정 속도 순위 |
| Checkpoint bytes·parameter bytes loaded | 파일 크기와 로드된 가중치 크기 | 활성화 메모리를 포함한 최대 RAM/GPU 메모리·전력 |

따라서 이전 안구 발표의 `training time`, `latency`, `trade-off`와 **비슷한 형태의 표는 만들었지만**, 실제 장비에서 측정했다는 뜻은 아니다. 런타임 대시보드의 Accuracy는 **과거 Validation 기록**, 지연 시간만 이번 Colab 실행의 새 측정이다.

## 각 그림을 보면 어떤 판단이 가능한가

Hair 6종의 네 조건은 같은 데이터 버전이므로 `hair6_tradeoff.png`의 위쪽(높은 Validation Accuracy)과 왼쪽(짧은 Colab p50)을 함께 볼 수 있다. B1·384·원본의 Validation Accuracy `0.7992337164750958`·p50 `409.83297050024703 ms`와 B0·256·증강의 `0.7777777777777778`·`288.73898249958074 ms`가 서로 다른 선택을 이끈다. 같은 6종 Test에서도 B1의 Macro F1 `0.8091500773460419`가 B0의 `0.8021613486071133`보다 높았다. 이는 **공개 데이터 분류 성능과 Colab 실행 비용의 교환 관계**다.

Web Skin의 PMG B1·384는 Val Accuracy `0.866`으로 B0·256의 `0.85`보다 높지만 Colab p50은 `419.9053944998923 ms` 대 `304.2439384998943 ms`로 길다. 선택한 Web Skin v2가 비용 균형 후보라는 이유를 수치로 설명할 수 있다. Hair 5종에서 SupCon B1·256의 p50 `398.9703649999683 ms`는 같은 기준선 `399.0923975006808 ms`와 거의 같으면서 Validation Macro F1은 더 높았다. 하지만 최종 B1·384 v2의 Validation 성능이 더 높아 후보는 유지됐다. Skin은 Clean 증강의 Validation Accuracy `0.982`가 Clean 원본 `0.973`보다 높았고, p50은 거의 같았다. **서로 다른 분류기끼리의 Accuracy가 높은 순서**로 모델 기술의 우수성을 평가해서는 안 된다.

`*_metrics_overview.png`의 색 지도는 각 열의 크기를 따로 정규화한다. 진한 색이 반드시 ‘좋음’을 뜻하지 않는다. 오른쪽 상자그림은 한 모델의 30회 변동이 아니라 **한 과제 안의 여러 모델 지연 시간 분포**다. `*_dashboard.png`의 초록 학습 시간 막대는 과거 실행 환경이 다른 기록이다. 초기에 만든 모델과 Clean 모델이 한 그림에 함께 있으면 **분할이 다른 점수는 연결선처럼 읽지 않는다**. 실제 해석은 [런타임 검토 보고서](../../docs/research/RUNTIME_BENCHMARK_REVIEW_20260928.md)의 그래프 설명을 따른다.

> “새 양호 사진을 검토해 Hair 6종 과제를 만들고 네 조건을 같은 분할에서 비교했습니다. 정확도 우선 B1·384 원본과 실행 비용 대안 B0·256 증강을 별도로 보존했습니다. 이어 저장 모델 34개를 Colab GPU에서 동일한 합성 입력으로 측정해 분류 성능과 실행 시간의 교환 관계를 확인했습니다. 실제 장비·실사용 사진의 성능과 지연 시간은 아직 측정하지 않았습니다.”
